# WedBar — детальная спецификация

> Источник истины по продукту — [SPEC.md](./SPEC.md). Этот документ уточняет и
> формализует его для реализации: фиксирует стек, модель данных, статусную
> модель, контракты API и декомпозицию. При противоречии сначала сверяемся со
> SPEC.md и решаем осознанно.

## 1. Обзор

Мини-приложение для свадьбы: гости сканируют QR на столе, попадают в меню
коктейлей и заказывают. Три раздела в одном приложении:

- **Бар** — заказ коктейлей для гостей (публичный, `/?table=N`);
- **Панель заказов** — рабочий экран бармена (случайный слаг);
- **Админка** — управление меню и статистика (случайный слаг).

Масштаб: ~100 гостей, один вечер, одна инсталляция. Приоритеты: визуал бара,
надёжность панели бармена, простота эксплуатации.

## 2. Стек и архитектурные решения

| Решение | Выбор | Почему |
| --- | --- | --- |
| Фреймворк | Next.js 16.2 (App Router), один проект на все 3 раздела | Уже в репозитории; конвенции этой версии отличаются — перед кодом читать `node_modules/next/dist/docs/` |
| БД | SQLite (better-sqlite3), файл `data/wedbar.db` | Один процесс, нулевая эксплуатация, синхронный API достаточен для нагрузки |
| Реалтайм | SSE через route handler | Однонаправленный поток (сервер → клиент) покрывает все нужды; проще WebSocket |
| Медиа | Файлы на диске в `data/uploads/`, отдача через route handler | Переживает редеплой, не попадает в git, не требует пересборки |
| Хостинг | Self-hosted: `next build && next start` за reverse-proxy (Caddy/nginx) с TLS | Пользователь в РФ, Vercel/Supabase исключены |
| Стили | Tailwind CSS 4 (уже подключён) | |
| Кэширование | `cacheComponents` НЕ включаем; все данные динамические | Route handlers по умолчанию не кэшируются — это нам и нужно |

Важно: SSE-шина живёт в памяти процесса (единственного), поэтому деплой строго
в один инстанс `next start`. В dev-режиме HMR может сбрасывать подписки — это
ожидаемо и не является багом.

Фактические имена сегментов — на усмотрение реализации, но принципы неизменны:
секретные разделы под слагами из env, медиа и БД вне git, API — route handlers.

### Секретные слаги

`BARTENDER_SLUG` и `ADMIN_SLUG` задаются в `.env` (длинные случайные строки).
Никакой другой авторизации нет (осознанное решение из SPEC.md). Разделы
не должны попадать в sitemap/robots и не должны ссылаться друг на друга из
публичной части.

## 3. Модель данных (SQLite)

```sql
CREATE TABLE drinks (
  id          TEXT PRIMARY KEY,          -- nanoid
  name        TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',  -- короткое описание для гостя
  ingredients TEXT NOT NULL DEFAULT '',  -- состав, видит гость
  recipe      TEXT NOT NULL DEFAULT '',  -- рецепт, видит только бармен
  media_path  TEXT,                      -- относительный путь в uploads/
  media_type  TEXT CHECK (media_type IN ('image','video')),
  position    INTEGER NOT NULL DEFAULT 0,-- порядок в ленте
  is_stopped  INTEGER NOT NULL DEFAULT 0,-- стоп-лист
  is_deleted  INTEGER NOT NULL DEFAULT 0,-- мягкое удаление (сохраняет статистику)
  created_at  TEXT NOT NULL
);

CREATE TABLE orders (
  id            TEXT PRIMARY KEY,        -- nanoid, попадает в localStorage гостя
  table_number  INTEGER NOT NULL,
  status        TEXT NOT NULL CHECK (status IN
                  ('pending','in_progress','delivering','done','rejected')),
  reject_reason TEXT,                    -- обязателен при rejected
  created_at    TEXT NOT NULL,
  accepted_at   TEXT,
  ready_at      TEXT,                    -- момент нажатия «Готово»
  closed_at     TEXT                     -- done или rejected
);

CREATE TABLE order_items (
  order_id   TEXT NOT NULL REFERENCES orders(id),
  drink_id   TEXT NOT NULL REFERENCES drinks(id),
  drink_name TEXT NOT NULL,              -- снапшот на момент заказа
  qty        INTEGER NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, drink_id)
);
```

Миграции — простым нумерованным скриптом при старте (`user_version` pragma).
Сид-скрипт (`npm run seed`) наполняет базу тестовыми напитками с
плейсхолдер-медиа — до появления реального контента.

## 4. Статусная модель заказа

```
pending ──принять──▶ in_progress ──готово──▶ delivering ──5 мин──▶ done
   │                    │
   └────отклонить───────┴──▶ rejected (с обязательным комментарием)
```

| Статус | Гость видит | Панель бармена |
| --- | --- | --- |
| `pending` | «Ожидает выполнения» | Карточка с кнопкой «Принять» |
| `in_progress` | «Выполняется» | Карточка с кнопкой «Готово» |
| `delivering` | «Доставляем» | Карточка исчезла с панели |
| `done` | Заказ в истории | — |
| `rejected` | Комментарий бармена, блокировка снята | — |

Правила:

- **Переход `delivering → done`** — автоматически через **5 минут** после
  `ready_at`. Сервер помечает лениво (при любом чтении заказа проверяет
  таймаут); клиент дублирует таймером для мгновенного UI.
- **Повторный заказ** разрешён гостю уже на статусе `delivering` (не ждём
  `done`) — как в SPEC.md.
- **Отклонение**: бармен может отклонить заказ в статусах `pending` и
  `in_progress` только с комментарием о том, что напиток ушёл в стоп-лист.
  UI отклонения: бармен выбирает позицию(и) заказа, попавшие в стоп — они
  автоматически ставятся в `is_stopped = 1`, комментарий формируется из
  названий («К сожалению, "Negroni" закончился») с возможностью дописать
  текст. Комментарий обязателен и показывается гостю на экране заказа.
- Статусные переходы валидируются на сервере (нельзя «Готово» из `pending`
  и т.п.); гонки двух вкладок панели разрешаются первым запросом, второй
  получает 409.

## 5. Бар (раздел гостя)

### 5.1 Вход

QR на столе ведёт на `https://<домен>/?table=N`. Номер стола сохраняется в
localStorage при первом заходе (если гость потом откроет без query — берём
сохранённый; если нет ни query, ни сохранённого — просим выбрать стол из
списка). Генерация QR — вне скоупа (владелец делает сам).

### 5.2 Лента напитков

- TikTok-стиль: вертикальный список, **одна полная страница экрана на
  напиток**, snap-скролл (`scroll-snap-type: y mandatory`).
- Контент страницы напитка: медиа на весь экран (изображение или зацикленное
  видео без звука, `playsinline muted loop`), поверх — название, короткое
  описание, состав, кнопка «Заказать».
- Кнопка «Заказать» по нажатию превращается в степпер `− N +` (первое нажатие
  = qty 1). Состояние корзины — в localStorage, переживает перезагрузку.
- Когда в корзине ≥ 1 позиции — плавающая кнопка перехода в корзину со
  счётчиком.
- Напитки в стоп-листе в ленте не показываются (если напиток ушёл в стоп,
  пока лежал в корзине — при оформлении сервер вернёт ошибку с указанием
  позиции, клиент удалит её из корзины и покажет сообщение).
- История заказов — небольшие плашки вверху экрана (номер + статус), по клику
  открывается экран заказа. Источник — список id в localStorage.

### 5.3 Корзина

- Список позиций: миниатюра, название, степпер количества, удаление.
- Кнопка оформления — **slide-to-order** (потянуть слайдер). Перед
  реализацией — короткий ресёрч accessibility, критерии отказа от слайдера:
  ложные срабатывания при скролле, конфликт со свайпом «назад» в iOS Safari,
  недоступность со screen reader без адекватного фолбэка. Обязательный
  фолбэк в любом случае: элемент доступен с клавиатуры/SR как обычная кнопка
  (role="button" + подтверждение). Если риски подтверждаются — обычная
  большая кнопка с шагом подтверждения.
- POST `/api/orders` идемпотентен по client-generated id (повторная отправка
  той же корзины не создаёт дубль).

### 5.4 Активный заказ и блокировка

- После оформления `orderId` пишется в localStorage как активный; UI
  переключается на экран ожидания, меню для заказа заблокировано.
- Экран ожидания: список позиций + индикатор из 3 этапов
  (ожидает выполнения → выполняется → доставляем), обновление по SSE
  с фолбэком на поллинг раз в 10 с.
- Блокировка снимается когда заказ в `delivering`/`done`/`rejected`.
  Это **чисто клиентское** ограничение: на каждой загрузке страницы клиент
  запрашивает `GET /api/orders/:id`; если заказ завершён, не найден или
  запрос упал с 4xx — запись удаляется и меню открывается.
- При `rejected` гость видит комментарий бармена крупно и понятно, затем
  может заказать снова.

## 6. Панель заказов (бармен)

- Один экран **без скролла**: сетка максимум из 6 карточек (планшет,
  landscape — основной сценарий; выживаемость на телефоне желательна, но
  вторична). Заказы в порядке `created_at` (FIFO). Если заказов больше 6 —
  седьмой появляется, когда освободится слот.
- Карточка: крупный **номер стола** (по нему бармен клеит стикер для
  официанта), список позиций (миниатюра + название + количество), время с
  момента заказа. Клик по позиции — модалка с рецептом (`recipe`).
- Низ карточки: кнопка «Принять» → после нажатия становится «Готово» →
  после «Готово» карточка исчезает (заказ уходит в `delivering`).
  Отдельная неакцентная кнопка «Отклонить» — сценарий из п. 4.
- Новые заказы прилетают по SSE без перезагрузки; звуковой сигнал при новом
  заказе (с кнопкой mute — автоплей звука требует первого взаимодействия).
- Сайдбар (кнопка-бургер): ссылки «Панель заказов» и «Настройки».
- Настройки = стоп-лист: список всех напитков с тумблером «в стопе».
  Изменение мгновенно влияет на ленту гостей (SSE-событие `menu.updated`).

## 7. Админка

### 7.1 Напитки

- Список всех напитков с сортировкой (порядок ленты, drag-and-drop или
  кнопки вверх/вниз), статусом стопа, редактированием и мягким удалением.
- Форма: название, описание, состав, рецепт, загрузка медиа (jpeg/png/webp/
  mp4, лимит ~50 МБ). Файл сохраняется в `data/uploads/<nanoid>.<ext>`,
  изображения при загрузке ресайзятся до разумного размера (sharp).
  Отдача — `GET /media/...` с `Cache-Control: immutable` (имя файла
  уникально на каждую загрузку).

### 7.2 Дашборд

Три блока (по ответам владельца):

1. **Топ напитков** — количество заказанных порций по каждому напитку
   (учитываются заказы, дошедшие до `delivering`/`done`).
2. **Заказы по времени** — таймлайн вечера, заказов по получасовым интервалам.
3. **Активность по столам** — количество заказов/порций по столам.

Плюс сводные цифры: всего заказов, всего порций, отклонённых. Обновление —
по SSE или кнопкой refresh; изощрённый реалтайм здесь не нужен.

## 8. API (контракты)

Все ответы — JSON; ошибки — `{ error: { code, message } }`.

| Метод и путь | Назначение | Примечания |
| --- | --- | --- |
| `POST /api/orders` | Создать заказ | `{ id, table, items: [{drinkId, qty}] }`; 409 если позиция в стопе (с указанием какая) |
| `GET /api/orders/:id` | Статус заказа для гостя | Лениво применяет таймаут `delivering → done` |
| `PATCH /api/orders/:id` | Смена статуса барменом | `{ action: 'accept' \| 'ready' \| 'reject', rejectReason?, stopDrinkIds? }`; валидация переходов, 409 при гонке |
| `GET /api/orders?active=1` | Активные заказы для панели | `pending` + `in_progress`, FIFO, limit 6 (+ количество в очереди) |
| `GET/POST/PATCH/DELETE /api/drinks...` | CRUD напитков, стоп-лист, порядок | Мутации доступны из панели (стоп) и админки |
| `GET /api/stats` | Данные дашборда | |
| `GET /api/events` | SSE | События: `order.created`, `order.updated`, `menu.updated`; формат `event: <type>\ndata: <json>` |

SSE-клиенты: панель бармена (заказы + меню), экран ожидания гостя (свой
заказ), лента гостя (меню/стоп-лист), дашборд. `EventSource` переподключается
сам; после реконнекта клиент делает полный refetch своего состояния —
события используются как сигнал, а не как единственный источник данных.

## 9. PWA

- Три независимых установки: бар, панель, админка. Конвенция Next кладёт
  `manifest.*` только в корень `app/`, поэтому манифесты панели и админки
  отдаём route handler'ами внутри их сегментов и подключаем через поле
  `manifest` в metadata соответствующего layout.
- `display: standalone`, `start_url` — корень своего раздела, свои имя/иконка/
  цвет темы на каждый раздел (bar — гостевой брендинг, panel и admin —
  утилитарные).
- Иконки 192/512 + apple-touch-icon. Оффлайн-режим не требуется: service
  worker минимальный или отсутствует (для installability в современных
  браузерах достаточно манифеста + HTTPS).

## 10. НФТ

- **Нагрузка**: ~100 гостей, пики в десятки одновременных пользователей —
  один процесс Next + SQLite (WAL mode) покрывает с большим запасом.
- **Безопасность**: соответствует SPEC.md — без авторизации; секретность
  панели/админки только за счёт слагов. В публичной части нет ссылок на них.
  Загружаемые файлы валидируются по типу и размеру.
- **Отказоустойчивость вечера**: перед событием — бэкап `data/`; при рестарте
  процесса состояние полностью восстанавливается из SQLite (SSE-клиенты
  переподключаются и делают refetch). localStorage гостей не зависит от
  сервера.
- **Мобильный веб — основная платформа** гостевой части: iOS Safari и
  Android Chrome обязательны к проверке (100vh/`dvh`, snap-скролл, автоплей
  видео, слайдер заказа).

## 11. Декомпозиция

Этапы последовательные, каждый заканчивается работающим приложением.

1. **Фундамент**: схема БД + миграции + сид, `lib/db.ts`, `lib/bus.ts`,
   SSE-endpoint, каркас роутов трёх разделов со слагами из env, отдача медиа.
2. **Бар: меню**: лента со snap-скроллом, страница напитка, степпер,
   корзина в localStorage, плавающая кнопка корзины.
3. **Бар: заказ**: ресёрч слайдера + реализация (или фолбэк), POST заказа,
   блокировка, экран ожидания со статусами по SSE, комментарий отклонения,
   история заказов плашками.
4. **Панель бармена**: сетка 6 карточек, FIFO-очередь, принять/готово/
   отклонить, рецепт, звук, сайдбар, стоп-лист.
5. **Админка**: CRUD напитков с аплоадом и сортировкой, дашборд (3 блока +
   сводные цифры).
6. **PWA и полировка**: манифесты и иконки трёх разделов, проверка на
   реальных мобильных, продакшен-сборка, инструкция по деплою
   (`docs/DEPLOY.md`: systemd + Caddy + бэкап).

## 12. Вне скоупа / на стороне владельца

- Генерация и печать QR-кодов (ссылки вида `/?table=N`).
- Реальный контент: фото/видео напитков, описания, рецепты (до этого — сиды).
- Домен, сервер и TLS-сертификат (инструкция будет в `docs/DEPLOY.md`).
